# V1.8.2 (2026-11-20): two window-layout fixes for scaled displays

A small follow-up to [1.8.1](V1.8.1.md), found by a test pass with a simulated 150 % display that also recorded every window's position and every control's position.

| File | Status |
|---|---|
| `WinSuperTool.ps1`, `WinSuperTool-NoAI.ps1`, `WinRepairTool-startup.ps1` | **changed**: both fixes |
| `WinFixKit.ps1`, `Collect-Logs.ps1`, `Monitor-Logs.ps1`, `ClaudeLogAnalyzer.ps1` | **changed**: fix 1 (shared window helpers) |
| launchers | unchanged |
| `tests/Toolkit.Tests.ps1` | 2 new checks (21 in total) |

| Sev | Fix |
|---|---|
| S3 | **Windows opened partly off the screen on a scaled display.** WinForms centres a window using its size *before* it scales, and the window then grows to the right and down. At 150 %, the WinSuperTool window and its System Info windows ran past the bottom of the screen. Every window is now centred again with its final size, and kept inside the screen (shrunk to fit if it is bigger than the screen). |
| S3 | **Controls inside tabs could end up in the wrong place, or overlap.** It showed on WinSuperTool's beta Automation tab, where "Preset" and "Save an HTML report" overlapped. Until a tab control's window exists, every tab page is a 200 x 100 placeholder. Controls anchored to the bottom or right of a page were measured against that placeholder, and moved by different amounts depending on when each was anchored. That also made the tab's scroll size wrong. WinSuperTool and WinRepairTool now create their tab control as soon as the tabs exist. (`CreateControl()` does nothing for a window that is not shown yet; reading `.Handle` does it.) |
